# 汐得时雨（Seed: TideRain）项目介绍文档

## 1. 项目概述

汐得时雨（Seed: TideRain）是一款面向学习、写作、编程与日常事务管理场景设计的沉浸式专注应用。项目以“专注—休息—记录—复盘—成长”为主线，将番茄钟计时、环境音营造、本地音乐播放、植物成长反馈、待办管理、习惯打卡、笔记便利贴、月历日记与个人统计等功能整合在同一套交互体系中，形成兼具效率管理与陪伴体验的数字专注空间。

与传统只强调倒计时或任务清单的工具相比，汐得时雨更重视专注过程的连续性与可感知性。一方面，系统以植物成长、语句陪伴、环境声景、背景氛围等机制强化情感化体验，使用户在完成任务的同时获得更柔和、更具沉浸感的使用感受；另一方面，系统通过专注轮次结算、热力图、连续天数、累计时长等数据指标构建可量化的反馈。

项目采用 React + TypeScript + Vite 构建前端应用，并结合 Electron 完成桌面端封装；在 Web 形态下，构建后的静态资源由 Express 托管，并额外提供 Gemini 相关 AI 接口。界面逻辑以组件化方式组织，核心状态由全局上下文统一管理，业务数据主要保存在浏览器本地存储中，本地音乐文件则通过 IndexedDB 进行持久化管理。整体架构轻量、部署成本低，既适合作为个人长期使用的效率工具，也具备课程设计、作品展示和后续扩展开发的良好基础。

从工程形态上看，当前项目主要支持三种运行方式：

- 纯前端开发态：仅启动 Vite，适合页面与交互开发；
- Web 生产态：前端构建产物与 Express 服务一起运行；
- Electron 桌面端：开发态加载本地 Vite 地址，打包后加载本地静态文件，并由主进程直接承担 Gemini 请求。

## 2. 建设背景与设计目标

在信息密集型学习与工作环境中，用户普遍面临以下问题：

1. 专注过程容易被打断，缺少稳定的节奏控制机制；
2. 待办、习惯、笔记、统计等功能分散在多个应用中，使用链路割裂；
3. 传统效率工具偏重机械记录，缺乏成长反馈与持续使用的情绪激励；
4. 本地化、轻量化和个性化不足，长期使用体验不够完整。

基于上述问题，汐得时雨确立了以下设计目标：

### 2.1 构建完整的专注闭环

项目不仅实现计时，还将休息切换、阶段结算、历史沉淀、月度统计和长期习惯追踪连接起来，使一次专注行为能够在系统内形成完整闭环。

### 2.2 提供沉浸式专注环境

通过声景预设、多轨混音、本地音乐、动态植物、背景图和细腻的视觉表现，降低用户对“效率工具机械感”的抵触，提高长时间使用时的舒适度。

### 2.3 强化过程反馈与成就感

系统将专注时长转化为好感度、植物成长阶段、周统计和热力图数据，使用户能够明确感受到投入带来的可视化成果。

### 2.4 本地优先与轻量部署

项目尽量减少对外部服务和重型后端的依赖。常规数据使用 localStorage 管理，本地音乐使用 IndexedDB 保存，适合个人设备长期积累与迁移备份。

### 2.5 兼顾可扩展性与工程化表达

在功能完成度之外，项目还重视代码组织、模块拆分与桌面端封装能力，为后续加入云同步、AI 复盘、多人协同等扩展功能预留接口空间。

## 4. 系统总体设计

### 4.1 总体架构

项目整体采用“前端主导 + 本地持久化 + 桌面封装”的轻量架构。其组织方式可概括为四个层次：

1. **界面呈现层**：基于 React 组件完成页面结构、交互响应和视觉呈现；
2. **业务控制层**：由全局状态上下文统一维护番茄钟、任务、习惯、音乐、日历、植物成长与界面状态；
3. **本地数据层**：普通业务数据持久化至 localStorage，本地音乐文件存入 IndexedDB；
4. **桌面运行层**：通过 Electron 将 Web 应用打包为桌面程序，支持开发态和生产态加载。

该架构具有三个明显特征：一是结构清晰，所有核心业务围绕统一状态流转；二是依赖本地环境即可运行，部署门槛较低；三是既能以浏览器方式使用，也具备桌面应用的交付形态。

### 4.2 页面与交互布局

主界面采用单页式布局，核心区域由顶部工具栏、左侧专注区、中部植物与陪伴区、右侧任务/习惯/笔记区组成。系统支持桌面端完整布局，也提供移动端面板切换式交互方案，以适应不同屏幕尺寸。

界面层的交互特点包括：

- 顶部入口集中承载日历与个人中心；
- 左侧聚焦计时与声音控制，减少专注过程中的界面跳转；
- 中部植物区域承担视觉焦点与陪伴反馈；
- 右侧工作区用于承接待办、习惯和笔记等高频管理动作；
- 首次使用时带有引导式教程，降低上手门槛。

### 4.3 路由与运行形态

项目采用基于 Hash 的轻量路由方案，其主要目的是兼容 Electron 环境下的 `file://` 资源加载方式，避免传统 History 路由在桌面封装场景中的路径解析问题。应用既可在开发服务器中运行，也可在构建后由桌面端直接加载静态入口页面。

### 4.4 全局状态设计

项目以 `GameContext` 作为业务核心，统一维护以下状态：

- 番茄钟参数、计时模式、剩余时间、轮次进度；
- 好感度、植物阶段、专注历史、热力图数据；
- 待办、标签、提醒、习惯、笔记、便利贴、日记；
- 场景音混音、本地音乐列表、音量、播放进度与循环模式；
- 背景图、当前激活面板等界面状态。

这种集中式状态设计保证了模块之间的联动一致性。例如，专注结算会同时影响好感度、植物成长、历史记录与热力图；待办提醒会自动生成便利贴；音乐播放状态又会同步写入本地缓存，以保证刷新或重启后的恢复能力。

### 4.5 工程目录与运行入口

目前仓库按职责大致分为以下几个部分：

- `client/`：前端应用与主要业务界面
- `server/`：Web 生产态所需的 Express 服务端
- `electron/`：Electron 主进程与 preload 桥接逻辑
- `shared/`：共享常量或通用逻辑
- `docs/`：项目文档
- `patches/`：`pnpm` 依赖补丁文件

常用运行入口包括：

- `npm run dev`：仅启动 Vite
- `npm run dev:desktop`：同时启动 Vite 和 Electron
- `npm run build && npm run start`：构建并启动 Web 生产态
- `npm run dist:win` / `npm run dist:dir`：打包 Electron 桌面端

其中，`npm run dev` 只适合前端开发，不适合作为 AI 功能调试入口；AI 调试通常应选择 `npm run dev:desktop` 或 `npm run build && npm run start`。

## 5. 核心功能模块设计

### 5.1 番茄钟专注模块

番茄钟模块是系统的运行核心。用户可自定义专注时长、休息时长与循环轮数，系统根据当前状态在专注与休息模式之间自动切换，并通过统一的状态机完成回合结算。

其实现并非简单的倒计时归零处理，而是将完整一轮番茄周期拆分为以下几个状态：

1. 专注阶段计时；
2. 阶段完成后进入休息；
3. 多轮番茄结束后统一结算本轮累计专注时长；
4. 将结算结果写入总时长、会话历史、连续天数、热力图与植物成长数据。

代码中还引入了“跳过按钮锁定”机制，用于约束随意快进操作，体现了项目对行为引导的考虑。刷新页面后，计时器会保留合法的剩余时间，但默认暂停运行，以避免刷新导致的误计时或状态错乱。

### 5.2 环境音与多轨混音模块

声景系统并非简单调用固定音频资源，而是使用 Web Audio API 程序化生成白噪音、棕噪音、粉噪音以及雨声、雷声、海浪、风声、鸟鸣、篝火、咖啡馆、图书馆、夜虫鸣等环境音层。系统通过主音量和多轨音量控制，实现声景预设与自定义混音两种使用方式。

在交互层面，项目预置了“深夜学习”“雨天咖啡馆”“清晨花园”“篝火夜话”“海边小屋”“暴风雨夜”等多个声景方案；在技术层面，则通过 `AudioContext + GainNode + 滤波器 + 振荡器 + 定时触发器` 的组合，模拟不同场景的声音质感与动态变化。该实现方式具有资源占用低、可调节性强和可扩展性好的优点。

### 5.3 本地音乐管理模块

除环境音之外，项目还提供本地音乐导入、播放控制、播放进度恢复、循环模式切换与播放列表重排序功能。音乐列表支持顺序播放、列表循环和单曲循环三种模式，并允许用户对当前播放进度进行拖动定位。

在持久化策略上，系统将音乐元数据存入主状态，将音频 Blob 文件存入 IndexedDB。页面刷新后，程序会主动校验每首音乐文件是否仍然存在，并根据校验结果为轨道标记“有效、缺失、加载中”等状态；若文件缺失，界面会提示重新上传。该设计有效解决了单纯依赖 Blob URL 时刷新后链接失效的问题，体现了对本地媒体持久化细节的深入处理。

### 5.4 植物成长与陪伴反馈模块

植物成长模块是本项目最具辨识度的设计之一。系统根据好感度数值设置“种子、嫩芽、幼苗、灌木、小树、花树”等多个阶段，每完成一定量的专注，植物便会逐步成长。相比单纯数字统计，这种可视化反馈更容易建立持续使用的心理激励。

在图形实现上，植物场景由 Three.js 程序化建模生成，而非依赖外部三维模型文件。花盆、土壤、种子、茎干、叶片、树冠等元素均通过几何体、曲线、材质与动画逻辑组合构建，既降低了资源依赖，又增强了作品的技术表达完整性。

此外，主界面还配有植物点击语句、阶段性对话和随机句库机制。系统根据当前状态动态选择展示语句，使植物不仅是静态图形，也承担一定的陪伴交互职责。

### 5.5 待办管理与提醒模块

待办模块支持待办内容编辑、标签分类、优先级管理、截止时间设置和提醒时间配置。与普通待办列表不同，系统会定时检查待办是否进入提醒时间窗口；一旦触发提醒，待办内容会被自动转换为便利贴式提示窗口，并同步更新提醒状态，避免重复提醒。

这种设计将“任务提醒”从传统列表中的被动信息，转化为更具可视性的主动反馈，提高了任务临近截止时的可感知程度。

### 5.6 AI 待办导入模块

项目提供了基于 Gemini 接口的待办抽取能力。用户可粘贴群聊或文本记录，系统通过预定义提示词要求模型只输出结构化 JSON，并从中提取真正需要执行的任务事项及其可能存在的截止时间。随后，结果会直接写入待办列表。

该模块的价值不在于简单接入第三方模型，而在于其与现有待办系统实现了闭环衔接：AI 输出内容被直接规范化为系统内部数据结构，从而降低了任务整理的人工成本。

从调用链路上看，当前项目中的 AI 导入存在两条实现路径：

- Web 路径：前端通过 `client/src/lib/todoAi.ts` 调用 `/api/ai/todos`，由 `server/index.ts` 代表前端向 Gemini 发起请求；
- Electron 路径：前端优先通过 `window.desktop.ai.generateTodos` 调用 preload 暴露的 IPC 接口，再由 `electron/main.mjs` 在主进程中直接请求 Gemini。

因此，同一套前端界面在不同运行形态下，AI 请求的真正后端并不完全相同：Web 形态依赖 Express，桌面端则依赖 Electron 主进程。

### 5.7 笔记与便利贴模块

笔记模块支持文本记录、内容编辑和删除，并可将笔记以便利贴形式拖入主界面。便利贴支持自由移动、尺寸调整、颜色切换和关闭操作，增强了界面的工作台属性。该模块适合承载临时想法、读书摘录、任务分解和学习提示等内容。

更进一步，系统将“普通笔记便利贴”与“待办提醒便利贴”统一纳入同一套视觉机制之中，使界面上的信息呈现方式具有较强的一致性。

### 5.8 习惯追踪与月历日记模块

习惯模块面向长期行为培养，支持每日打卡、连续天数统计、累计完成次数统计以及按周展示完成情况。系统通过日期集合计算习惯连续性，能够较准确地反映用户的短期坚持与长期积累状况。

月历模块则承担复盘功能。系统会按日期展示当日专注分钟数与完成番茄数，并支持用户记录日记内容。月度视角下，用户可以同时观察专注密度、任务完成情况与文字记录，形成更加完整的行为回顾界面。

### 5.9 个人中心与数据管理模块

个人中心汇聚系统配置与统计信息，主要包括：

- 本周专注数据与趋势展示；
- 近 180 天热力图；
- 累计专注时长、番茄数量、连续天数等指标；
- 习惯完成情况统计；
- 番茄钟参数与跳过键锁定配置；
- AI 导入所需密钥配置；
- 背景图上传、自动裁切与恢复默认；
- 数据导出、导入与清空。

其中，背景图处理并非简单上传后直接使用，而是先基于当前窗口比例进行裁切和重新编码，以保证不同设备下的视觉一致性。

## 6. 关键技术实现

### 6.1 状态机式番茄钟结算逻辑

项目的番茄钟实现采用了较明确的状态流转逻辑。专注阶段完成后并不立即将全部结果写入总数据，而是先累积本轮专注秒数与番茄数；只有当一轮结束或达到用户设定的循环次数后，系统才统一结算总专注分钟数、好感度、连续天数、热力图与会话历史。该设计避免了多轮专注中途切换带来的统计碎片化问题，也使得“完成一整轮专注”具备更清晰的行为语义。

### 6.2 Web Audio API 声景引擎

项目在声音部分采用了程序化音频生成策略。不同环境声通过噪声缓冲区、滤波器、低频振荡器、增益节点和定时触发器组合构成。例如：

- 雨声通过棕噪声叠加高通/低通滤波与随机水滴音模拟；
- 雷暴声通过低频滤波后的噪声脉冲与长尾衰减实现；
- 海浪与风声通过缓慢调制形成动态起伏；
- 咖啡馆与图书馆场景通过底噪与随机事件音叠加构建空间感。

这说明项目在声音设计上已经从“播放素材”上升到“构造声场”的层面，技术表达较为完整。

### 6.3 音乐文件持久化与校验机制

本地音乐模块通过 IndexedDB 建立独立存储空间，并采用单例数据库连接避免频繁打开连接带来的性能和稳定性问题。程序在启动时会主动恢复已保存的音乐列表，重新为每个 Blob 创建可用 URL，并对文件是否存在进行校验；对于刷新频繁发生的音频状态，则额外使用即时写入机制保存当前曲目和播放进度，减少刷新导致的状态丢失。

这一机制体现出较强的工程意识：一方面利用主状态防抖写入减少存储压力，另一方面又对音频相关状态采用更高频率保存策略，确保播放体验稳定。

### 6.4 Three.js 程序化植物建模

Three.js 场景中的植物不是固定资源展示，而是通过参数化几何建模生成。代码中使用球体、圆柱、圆环、曲线管道、平面几何和材质配置构建花盆、土壤、树干与叶片，并通过阶段映射控制植物的视觉状态。程序化建模使得项目在视觉呈现上具有更高的原创性，也为未来增加更多成长阶段或皮肤主题提供了可扩展基础。

### 6.5 本地优先的数据持久化策略

系统将不同类型数据分层存储：

- 高频、轻量的业务状态保存在 localStorage；
- 体积较大的本地音乐文件保存在 IndexedDB；
- 音频进度和选曲状态额外即时缓存，提升恢复可靠性。

这种分层策略兼顾了读写效率、实现复杂度与用户本地可控性，符合轻量桌面工具与本地效率应用的实际需求。

### 6.6 结构化 AI 输出接入方式

AI 待办导入模块并未将大模型输出直接显示给用户，而是通过约束提示词、限定 JSON 响应结构、提取字段并进行日期规范化，最终将结果转换为系统内部待办对象。此种接入方式避免了自由文本输出带来的不可控性，体现了“模型能力服务于业务结构”的实现思路。

### 6.7 Web 后端与桌面端的 AI 服务分工

在当前架构中，Gemini 调用并不是单一服务统一完成的，而是按运行形态分工：

- Web 生产态下，Express 同时承担静态资源托管与 AI 接口服务，提供 `GET /api/ai/config`、`POST /api/ai/config` 和 `POST /api/ai/todos`；
- Electron 桌面端下，主进程通过 IPC 直接提供 AI 能力，不经过 Express；
- 前端通过统一封装自动选择调用路径，从而避免业务层区分 Web 与桌面端细节。

这种设计让前端界面保持一致，但也意味着排查 AI 问题时需要先确认当前应用运行在哪种模式下。

### 6.8 环境变量、代理与 `.env` 查找规则

项目当前支持通过 `.env` 配置 Gemini Key 和代理，关键字段包括：

```env
GEMINI_API_KEY=
HTTP_PROXY=
HTTPS_PROXY=
NODE_USE_ENV_PROXY=
```

其中：

- `GEMINI_API_KEY` 用于 Gemini 鉴权；
- `HTTP_PROXY` / `HTTPS_PROXY` 用于代理访问；
- `NODE_USE_ENV_PROXY` 用于控制是否启用 `.env` 中的代理配置。

在查找配置时，代码都会先读取 `process.env`，只有在系统环境变量中没有命中时才继续查找 `.env` 文件。

Web 后端通常会按以下顺序查找：

1. 当前进程环境变量；
2. 当前工作目录下的 `.env`；
3. 由服务端文件相对路径推导出的 `.env`。

Electron 主进程在打包后通常会优先关注以下位置：

1. `userData` 目录下的 `.env`；
2. 可执行文件同目录下的 `.env`；
3. 当前工作目录下的 `.env`；
4. 由主进程文件相对路径推导出的 `.env`。

其中 `userData` 路径由 `app.getPath("userData")` 决定，在 Windows 上通常位于 `C:\Users\用户名\AppData\Roaming\应用名`。

这意味着：

- Web 端更适合在项目根目录放置 `.env`；
- 打包后的 Electron 更适合在 `.exe` 同目录或 `userData` 目录放置 `.env`；
- 如果代理项为空，则不会额外配置代理。
